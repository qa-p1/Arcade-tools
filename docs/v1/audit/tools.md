## Findings
### TL-1 (broken) CLI shortcut overlay crashes with SIGBUS after the AppImage command exits
Method: real AppImage CLI + private Xvfb + `coredumpctl` for the exact test-owned PID. With private resident running, run the installed private `Arcade-Tools.AppImage --show-shortcuts`. Exit code is 0, stdout empty, but no overlay appears. PID 139174 dumps core with SIGBUS / BUS_ADRERR. Its command is the helper inside the CLI's short-lived `.mount_ArcadefJEJNN`, not the resident's live `.mount_ArcadeeAdjgM`. Resident Super+/ opens the helper correctly from the live mount.
Expected: the advertised CLI opens a usable overlay. Actual: success exit masks a crashing helper. Evidence: `tools/r-overlay-cli-core.txt`, `r-overlay.png` (absent) versus `r-overlay-hotkey.png` (working).
Suspected cause: `src-tauri/src/main.rs:101-107` calls `hotkey::launch_overlay` then immediately returns; `hotkey.rs:21-37,40-45` discovers and spawns the inner executable in this mount. It does not ask the running resident to launch it or retain the mount until helper exit.

### TL-2 (UX) Shortcut overlay closes on focus loss
Method: GUI in private Xvfb. Open the overlay through resident Super+/, focus the overlay once, move the pointer away (stays open), then explicitly focus the private Audit Receiver. Within about 150 ms the overlay closes. Expected owner rule: a focus blip must not dismiss it. Evidence: `tools/r-overlay-hotkey.png`, `r-overlay-real-leave.png`, `r-overlay-real-blur.png`.
The raw packaged overlay can also crash (TL-5); a repeat with a command-scoped host-XKB preload reproduced clean focus-loss exit 0, isolating the dismissal policy from that crash (`r-overlay-control.txt`).
Source: `crates/arcade-tools-overlay/src/ui/desktop.rs:239-241` arms a 150 ms dismissal on `WindowEvent::Focused(false)`; the event loop consumes the deadline and closes it. Real compositor pointer-follow-focus is untested.

### TL-5 (broken) Typing in the packaged X11 shortcut overlay crashes in libxkbcommon
Method: GUI in private Xvfb with the helper launched from the **resident's still-live mount** (separate from TL-1). Open the overlay, focus it, type `clip`. It exits with SIGSEGV (PID 144184). Other packaged runs also crashed on receiving focus/key events (PIDs 139831, 139938, 141005). Expected: filter shortcuts without crashing. Evidence: `tools/r-overlay-direct.png`, `r-overlay-direct-query.png`, `r-overlay-segv-core.txt`, `r-overlay-segv-stack.txt`, private `logs/overlay-direct.log` copied later.
GDB puts the fault at `xkb_keymap_key_repeats` in the **bundled** `usr/lib/libxkbcommon.so.0`; the same process also maps the **host** `/usr/lib/libxkbcommon-x11.so.0`. A/B diagnosis: launch the **same packaged helper** with the command-scoped `LD_PRELOAD=/usr/lib/libxkbcommon.so.0`, keeping its resident mount alive. The same focus and typing `clip` now work, and Escape exits normally (0). No installed file was changed. This strongly implicates mixed host/bundled XKB libraries. Evidence: `r-overlay-host-xkb-query.png`, `r-overlay-host-xkb-escape.png`, private overlay-host-xkb.log copied later. `crates/arcade-tools-overlay/src/ui/desktop.rs:42-45,203-205,277` enters winit's X11 event processing. Exact bundled-library build provenance needs the packaging pipeline.

### TL-8 (broken) Home page re-hashes every installed AppImage every 2 seconds (explains the owner's ~9% idle CPU, T1)
Method: private profile with Tools 0.4.6 and 7 other Arcade AppImages installed through each app's own `--install --silent --no-launch` (489 MiB in total, all running in background); `/proc/<pid>/stat` ticks and `/proc/<pid>/io` over 20-60 s windows, window closed, on other pages, and on Home.
Steps: start Tools `--background`, open the window, press "Skip setup"/"Go to Home", sample; then click Apps and sample again.
Expected: an idle Home page costs next to nothing. Actual: window closed 0.000% CPU; any other page 0.000%; **Home visible: 12.3% CPU over 60 s, all of it in two tokio worker threads, and 3995 MiB read in 20 s** (about one full read of every installed AppImage per 2 s tick). Leaving Home returns to 0 MiB / 0%. This matches the owner's ~9% "idle" with several apps installed.
Cause (source): `src-ui/tabs/Home.svelte:66-72` polls `api.dashboard()` every 2000 ms while Home is active; `src-tauri/src/hub.rs:311` calls `Metrics::sample` which runs `manager.list(false)` (`src/dashboard.rs:41`); `list_catalog` calls `self.record(id)` for each app (`src/manager.rs:1396`); for an app that has a receipt but no Tools-written record (every app that is "Installed outside Arcade Tools", i.e. not yet "Let Tools manage it") `record()` falls to `record_from_receipt`, whose `checksum(&executable)` (`src/manager.rs:1163`; the mismatch branch at `1036` is also uncached) is a full uncached SHA-256 of the AppImage. The cached path (`cached_checksum`, `manager.rs:276`) is not used there, nor in the mismatch branch at `manager.rs:1036`. Home's health notice (`hub.rs:326`, `src/manager.rs:1894`) calls `list` again whenever `apps` changes. Managed apps with `record.version == receipt.version` short-circuit and are cheap, so the cost scales with the number of unmanaged apps.
Also (does not explain the CPU): each 2 s sample opens a fresh Link client to every installed app (`dashboard.rs:57-66`), so each peer spawns and tears down an `arcade-link-conn` thread twice a second; and `sysinfo` keeps one `/proc/<pid>/stat` file descriptor per tracked process (`dashboard.rs:52`; 1 fd seen in the private run, 8 in the owner's earlier process).
Thread/fd census, answering the question about growth: 7 `tools-tray` and 7 `arcade-link-con` threads for 7 running peers, not a leak. `tools-tray` is one event-loop thread (`src-tauri/src/tray/mod.rs:128`) plus one watcher thread per connected peer (`tray/mod.rs:311`, unnamed, so it inherits the comm name `tools-tray`); `arcade-link-conn` is the Link server's per-connection thread (`Arcade-link .../server.rs:452`), one per peer that keeps a connection to Tools' tray host. Both exit when the peer disconnects (`watch_peer` loop ends on error and sends `Event::Disconnected`). No per-install runtime or thread is started: install work uses the shared Tauri blocking pool (`desktop.rs:375` and `tauri::async_runtime::spawn_blocking`), and 24-26 `tokio-rt-worker` threads appear whenever Home is open and the pool is busy with those samples. The owner's 29 workers and 6+6 threads after several installs fit that census: more running peers means more threads, plus a larger blocking pool under Home polling. Nothing polls `/proc/<pid>/stat` in Tools source except a one-shot liveness read (`src/manager.rs:3133`), which closes the file.
Evidence: tools/r2-home-polling-measure.txt, r2-t-home3.png. Reading the owner's live Tools earlier in this session (read-only /proc): 8 `tools-tray`, 8 `arcade-link-con`, 8 `/proc/<pid>/stat` fds, lifetime CPU 2.1% over 5 h (no sustained burn at that moment).

Check for updates to switch versions." There is no Nightly badge on the card or in Updates. The select shows the chosen channel, not the installed one, so a user cannot tell which channel they are actually running.

The switch itself is wired and permits a downgrade back to stable (`src/updates.rs:405-428` `is_newer` returns true when `installed.channel != release.channel`) but only after an update check and install, and only on a network I cannot reach, so the install step is unconfirmed here.

### TL-11 (broken, source only) Every download is capped at 120 seconds in total
Source: `src/source.rs:105-106` builds the blocking client with `.timeout(Duration::from_secs(120))`, which in reqwest covers connecting through the end of the response body. `download()` streams the installer through that same client (`source.rs:404-445`). A 94 MiB Tools AppImage needs >6.3 Mbit/s sustained, a 52 MiB app >3.5 Mbit/s; slower links fail with "The download was interrupted. Check your internet connection and try again." with no resume (there is no Range request anywhere in `source.rs`), every attempt restarting at zero. Not reproducible offline (the loopback test server is debug-only); confidence is medium-high from the reqwest contract.

## Backend / performance
Fresh background idle does **not** reproduce ~9% CPU (the reproduction is Home-page polling, TL-8): no thread accumulated any CPU tick during 30 seconds. Thread names include 12 tokio workers, 2 tools-tray, 2 tools-shortcut-* and 2 arcade-link connections; duplication still needs explanation. Home with one live peer sampled 0.17% CPU / 78 threads over 30 s (`r-metrics-home.json`), still far below the reported 9%. See `tools/r-idle-background.json` for the full isolated thread/fd inventory. Never infer a CPU loop from worker count alone.

## Updater and stable/nightly channel walkthrough
Source walkthrough only (the release build has no test-server hook; network is blocked). Line numbers are in `~/Work/Coding/Rust/Arcade-tools`.

**Catalog.** `src/catalog.rs:13-18` fetches `raw.githubusercontent.com/qa-p1/Arcade-catalog/main/catalog.json` (1 MiB cap, ETag-conditional, cached envelope, compiled snapshot fallback; only owner `qa-p1` repos accepted). Offline Apps/Updates pages work from the snapshot (verified: Apps shows 7 apps, Updates reports "network: Couldn't connect" without breaking).

**Check.** A single scheduler thread (`src-tauri/src/hub.rs:104-140` (loop at 123)) wakes at `updates.next_check`: first check 60 s after process start, then every 6 h (`src/updates.rs:12-15`), plus on window open if the last check is older than 1 h, plus manual. Skipped entirely when `manager.paths.isolated`. Only the channel the user follows is checked per app (`updates.rs:289-360`), via `Source::check_repo_conditional` (`src/source.rs:268-345`): GitHub API `releases/latest` for Stable, `releases/tags/nightly` for Nightly, with the cached ETag (304 reuses the cache and does not count against the rate limit). On API rate limit it falls back to `github.com/.../releases/latest/download/arcade-release.json` or `.../download/nightly/...` (`source.rs:131-176`). The release must carry exactly one `arcade-release.json` and one asset matching the manifest; the manifest is schema-checked (`src/release.rs:112-160`) and an asset is chosen per OS/arch (AppImage on Linux, Tarball only for Clipboard/Shelf, never deb/rpm).

**Channel mapping.** `Channel` has exactly two values, `Stable` and `Nightly` (`release.rs:9-14`). Stable = GitHub "latest" release whose tag starts with `v`, is not a draft or prerelease, and equals `v<manifest version>` (`source.rs:338-345`). Nightly = the single moving release tagged exactly `nightly`. Consequences: a prerelease such as `v1.0.0-rc.1` is invisible to Stable by two independent checks (GitHub's `/latest` never returns prereleases, and `source.rs:340` rejects `prerelease`); no code lists releases to find an rc, and `release_history` (`source.rs:228`) is display only. There is no `test`/rc channel and no UI or preference value for one.

**Stored state.** `Preferences.channels: map app-id -> Channel` in `data/arcade/tools/preferences.json` (`manager.rs:386` `set_channel`, no network). The installed channel lives in the install record (`data/arcade/tools/<id>.json`, field `channel`) and the app's own receipt. `checked()` (`manager.rs:1418`) picks the selected channel (`prefs.channels` else record channel else Stable), caches the validated release at `cache/arcade/tools/releases/<id>/<channel>.json`. `updates::is_newer` (`updates.rs:405-433`) returns true whenever installed channel differs from the selected one, so switching Nightly to Stable offers the newest stable even when its version is lower, and the reverse. `Operation::Update` carries the reviewed channel/version and refuses with `state_changed` if either moved (`manager.rs:2180-2200`, `state_changed`).

**Download.** `Source::download` (`source.rs:404-445`): one plain GET of the asset URL (redirects limited to github.com/objects/release-assets hosts, max 8), streamed in 64 KiB blocks to a `NamedTempFile` in `cache/arcade/tools/downloads`, cancel flag checked each block, 1 GiB cap, then `fsync` and `verify()`: exact size when the manifest gives one and SHA-256 (`release.rs:263-275`). There is no Range request, no resume, no chunking, no piece store: any interruption (including the 120 s total timeout, TL-11) discards the temp file and the next attempt restarts at 0. A truncated or corrupt file fails verification with "Nothing was installed." and the temp file drops with the error. Interrupted leftovers from a killed Tools are removed at startup (`manager.rs:1059-1080`, tested in TL-7).

**Stage, swap, roll back.** `installation::retain` (`installation.rs:37-75`) copies the verified file to `cache/arcade/tools/installers/<id>/<sha256>.AppImage` (never deleted, TL-7) and re-verifies. `apply_package` -> `install_package` (`manager.rs:2295-2480`): stop the running peer, `Transaction::begin` snapshots old executable/receipt/integration, run the app's own `--install --silent --channel <c> --no-launch` from the retained copy, check the app wrote a matching receipt and that the installed executable hash equals the verified bytes, write the record, relaunch in the previous mode, `claim` the receipt, then `transaction.commit`. On any error the snapshot is restored and the old app relaunched; history records `Failed`, `RolledBack` or `RollbackFailed` (`manager.rs:2073-2110`). User rollback re-installs the retained previous package (`rollback_inner`, `manager.rs:2747`) and remembers the rolled-back-from version so auto-update skips it (`manager.rs:484-520`).

**Auto-update.** Opt-in per app (`set_auto_update`), runs only when idle (10 min after last use, busy peers refused) in the scheduler thread (`hub.rs:150-230`).

**Self-update of Tools.** `prepare_self_update_locked` (`manager.rs:713-795`): same check/download/retain, then writes a plan (`state/self-update/<token>.json`: package, expected version/path/hash, mode, parent pid), the desktop launches `arcade-tools --finish-self-update <plan>` as a detached helper (`hub.rs:214`) and exits. The helper (`finish_self_update`, `manager.rs:827-935`) waits up to 30 s for the parent pid to die, re-verifies package, old executable hash and class, runs the same transaction, relaunches the old Tools on failure, appends history. Evidence that it works in practice: the owner's real Tools (pid 1355) was replaced during this session by a `--wait-for-process 1355 --background` helper that I only observed. Dev builds and unmanaged installs are never replaced.

**What a partial or failed update looks like.** Network drop: "The download was interrupted..." (code `network`) and, in the scheduler, `transport_failed` stops further apps in that round and records `last_failure`; Updates page then shows "The last check didn't finish: network: Couldn't connect..." (r2-t-upd1.png, verified). Checksum failure: `checksum` error, nothing installed. 404 on nightly: reported as "No nightly release is published for this app" (not a failure).

**Gaps against the v1 plan.**
1. Delta/chunked updates: absent. No Range requests, no content-defined chunking, no shared piece store, no fallback ladder; every update is a full download of 50-94 MiB, and a flaky link restarts from zero.
2. Nightly as a per-app switch: half there. A per-app Stable/Nightly select exists (Apps card and Details) and `is_newer` supports crossing channels, but selecting only stores a preference (TL-9): no replacement install, no Nightly badge, no distinction between selected and installed channel in the UI. "Nightly" is a single moving GitHub release tag, not a promoted build.
3. Hidden rc `test` channel: not offered. `Channel` has no third value, stable rejects prereleases, no listing API, no preference value. Adding it needs a new enum value, a release listing path (`/releases` instead of `/latest`), and UI that never shows it.
4. Retention: unbounded SHA-named installer cache (TL-7).
5. Rate-limit handling is good (ETag, github.com fallback); the 6 h timer is backed off even after an offline failure, so the first window-open check after reconnect is what recovers (`updates.rs` `run_due` sets `next_check` before the request).

## Isolation artefacts seen in this resume pass (not product bugs)
- With HOME under `/tmp`, Tools reports "Automatic integration repair ... needs a permanent installed app" and Home lists every app as "runs from Downloads or a temporary location" (10 notices). Using the short symlink path for HOME instead gives "Refusing symlinked install or data path", so the private profile uses the resolved path.

- No XDG portal, DRI3 or accessibility bus: harmless WebKit/Mesa warnings. Arcade Clipboard started in the profile never published a Link endpoint on this headless display (Clipboard audit), so Tools shows it as "Not running".
- Observation for Shelf, not Tools: `Arcade-Shelf.AppImage --install --keep-download` fails with "Unknown option 'keep-download'" while every other app accepts it.
